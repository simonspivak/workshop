## Supabase

### Auth rate limit — /auth/v1/token (sign-in with password AND refresh) is one per-IP token bucket
- Supabase Auth limits `/auth/v1/token` per IP address: 1800 requests per hour, token bucket with capacity (burst) 30; bucket refills at the configured rate (1800/h = 30/min = 0.5/s). When empty → HTTP 429. In the GoTrue source the password grant does NOT get its own limiter: `internal/api/token.go` sets `limiter := a.limiterOpts.Token` and the `case "password": // set above` branch keeps it, same as `refresh_token`; only `web3` switches limiter. `internal/api/apilimiter/apilimiter.go` builds `Token` as `gc.RateLimitTokenRefresh/(60*5)` with burst 30, TTL 1h; `internal/conf/configuration.go` default `RateLimitTokenRefresh float64 default:"150"` (150 per 5 min = 1800/h). So password sign-ins and refreshes from one IP share the same 30-token bucket. Docs table marks it 'Customizable: No', but the same page's Management API PATCH example includes `rate_limit_token_refresh`, so it may be adjustable via `PATCH /v1/projects/{ref}/config/auth`.
- **Для нас:** app/(platform)/login/actions.ts:49 calls signInWithPassword server-side, so GoTrue keys the bucket on the Vercel function's egress IP, not the student's. 10 students in 2 min: ≤10 (+ a few wrong-password retries) requests → inside the 30 burst, no problem even if all share one IP. 50 students in 2 min: capacity ≈ 30 burst + 60 refilled over 120 s ≈ 90 requests if all from ONE IP → OK only if ≤ ~40 extra failed attempts; if logins cluster into ~30 s the capacity is 30+15=45 < 50 and the last ~5–10 students get 429, which actions.ts:52 maps to TOO_MANY ('Подождите пару минут'). Severity: high at 50 (some students see errors; lesson start delayed), low at 10. Fix: (1) in actions.ts, on `error.status === 429` retry once after ~2 s before surfacing TOO_MANY, and show a message that says 'попробуйте через 10 секунд' rather than 'пару минут'; (2) have the teacher log students in two waves of 25 ≥ 1 min apart (documented procedure in setup.md); (3) on Pro, raise `rate_limit_token_refresh` via Management API (verify it applies); (4) do NOT expect client-side sign-in to fix this: the whole room shares one public IP, so a browser-side signInWithPassword would hit exactly the same per-IP bucket.
- Источник: https://supabase.com/docs/guides/auth/rate-limits (via Supabase docs MCP, 2026-11-08); https://supabase.com/docs/guides/deployment/going-into-prod#auth-rate-limits (2026-11-08); GoTrue source raw.githubusercontent.com/supabase/auth/master/internal/api/token.go, internal/api/apilimiter/apilimiter.go, internal/conf/configuration.go (2026-11-08) · уверенность: high

### Which IP GoTrue sees for server-side calls; supabase-js/ssr do not forward the client IP
- GoTrue determines the IP as: `sbff.GetIPAddress(r)` (the `Sb-Forwarded-For` header, only when the project flag `security_sb_forwarded_for_enabled` is on) else first valid entry of `X-Forwarded-For`, else `RemoteAddr` (internal/utilities/request.go). Supabase docs: 'By default, Supabase Auth uses the IP address of the client for rate limiting... To use a forwarded IP address set the `Sb-Forwarded-For` header to the end-user IP address and make a request with a secret API key. Publishable API keys and legacy anon/service_role keys are not supported. IP address forwarding must be explicitly enabled for new projects (Authentication > Rate Limits > IP Address Forwarding).' supabase-js sends only `X-Client-Info` by default (packages/core/supabase-js/src/lib/constants.ts DEFAULT_HEADERS) and @supabase/ssr adds `X-Client-Info: supabase-ssr/<v> createServerClient` (node_modules/@supabase/ssr/dist/main/createServerClient.js:29); neither sends X-Forwarded-For or the client IP.
- **Для нас:** lib/server/supabase/server.ts:18 creates the login client with the publishable key, so even if we set `sb-forwarded-for` from headers() it would be ignored per docs. Our own IP-based counter (lib/server/rate-limit.ts:17-22, actions.ts:43-46) correctly compensates for brute-force protection, and it keys on the Vercel-provided `x-forwarded-for` (lib/server/bot/ratelimit.ts:36-40), which is the real student IP. Severity: medium (design constraint, not a bug). Fix options: (a) keep server-side login and accept Vercel egress IPs (see Vercel fact — they are dynamic, which actually spreads load over several buckets); (b) if 429s are observed, enable 'IP Address Forwarding' in Authentication > Rate Limits and perform ONLY the `signInWithPassword` call with a secret-key client that sets `global.headers['sb-forwarded-for'] = clientIp`, then hand the returned session to the cookie-based publishable client via `auth.setSession()`; never use that secret-key client for `.from('profiles')` (actions.ts:57) or RLS is bypassed.
- Источник: https://supabase.com/docs/guides/auth/rate-limits#ip-address-forwarding (2026-11-08); raw.githubusercontent.com/supabase/auth/master/internal/utilities/request.go and internal/sbff/sbff.go (2026-11-08); raw.githubusercontent.com/supabase/supabase-js/master/packages/core/supabase-js/src/lib/constants.ts (2026-11-08); local node_modules/@supabase/ssr · уверенность: high

### Classroom NAT: all students share one public IP regardless of login architecture
- Supabase per-IP limits key on the IP the Auth server sees. From the classroom, 10–50 browsers behind one router present the same public IPv4 (or one IPv6 /64). Vercel functions, by contrast, make outbound requests 'from a dynamic range of addresses... each invocation can exit from a different server'; a fixed outbound IP (Static IPs) exists only on Pro/Enterprise and excludes Routing Middleware.
- **Для нас:** Moving sign-in to the browser (createBrowserClient) would NOT raise capacity for a single room: 50 students → one IP → same 30-burst/1800-h bucket on /token; it only isolates different rooms from each other. Server-side login on Vercel Hobby spreads requests over a dynamic egress range, so in practice the per-IP bucket is probably hit less often than from the room — but the pool size per region is undocumented, so treat it as 'likely helps, not guaranteed'. At 10: no issue either way. At 50: plan the two-wave login and the 429 retry (previous fact). Severity: high at 50 if ignored. Our own limiter lib/server/rate-limit.ts:21 allows 100 attempts per IP per 15 min: 50 students with one typo each = 100 → the next attempt from the room is blocked for 15 minutes. Raise LOGIN_LIMITS.ip to ≥300 for IPv4 (or key the account limit only and keep IP limit as a sanity cap of e.g. 600/15 min).
- Источник: https://vercel.com/guides/how-to-allowlist-deployment-ip-address and https://vercel.com/docs/connectivity/static-ips (via WebSearch summary, 2026-11-08); Supabase rate-limits doc (2026-11-08) · уверенность: medium

### Token refresh load during a 75-minute lesson
- Access tokens default to 3600 s (`JWT.Exp` set to 3600 in ApplyDefaults; supabase/config.toml:40 `jwt_expiry = 3600`). Supabase recommends keeping 1 h and never below 5 min. Refresh requests hit the same `/auth/v1/token` per-IP bucket (1800/h, burst 30). auth-js refreshes proactively (AUTO_REFRESH_TICK 30 s, EXPIRY_MARGIN = threshold × tick) only in browser clients; server clients refresh lazily when the token is near expiry during getClaims().
- **Для нас:** proxy.ts:57 runs getClaims() on every matched request (/app, /teach, /admin, /login, /b, /api except /api/tg). A refresh happens roughly once per student per hour → 10 or 50 refreshes spread across 75 min from Vercel IPs: negligible against 1800/h. Severity: low. No change needed; do not lower JWT expiry below 1 h (it multiplies refreshes against the same bucket as logins).
- Источник: https://supabase.com/docs/guides/auth/sessions (2026-11-08); GoTrue internal/conf/configuration.go (2026-11-08); local node_modules/@supabase/auth-js/dist/main/lib/constants.js:6-21; supabase/config.toml · уверенность: high

### Refresh token rotation, reuse interval, two tabs / two devices
- Refresh token rotation is on by default (`RefreshTokenRotationEnabled default:"true"`); a refresh token can be reused within the reuse interval, default 10 seconds (config.toml:42 `refresh_token_reuse_interval = 10`; docs: 'we do not recommend changing this value'). Two exceptions prevent false revocation: reuse within 10 s, and using the parent of the currently active token returns the active token. Any other reuse marks the whole session's refresh tokens revoked. 'By default [a session] lasts indefinitely and a user can have an unlimited number of active sessions on as many devices.' Time-boxed sessions, inactivity timeout and 'Single session per user' are Pro-only and off by default; enforcement happens at next refresh, so effective duration = setting + JWT expiry.
- **Для нас:** Two tabs in one browser share the `sb-*` cookie; at expiry both tabs' requests cause proxy.ts:57 refreshes with the same refresh token — covered by the 10 s reuse window and the parent-token exception, so no random logouts. Same login on two devices (our test with two browsers): two independent sessions, each with its own refresh chain → both keep working; this stays true at 10 or 50 students. Risk only if someone later enables 'Single session per user' (Pro): the earlier device is logged out within ≤1 h. Severity: low. Recommendation: leave rotation/reuse defaults; do not enable single-session; in docs/platform/setup.md note that one card can be used on two devices and that a logout on one device does not log out the other (signOut default scope is global in auth-js — verify desired scope; actions.ts:69 uses default).
- Источник: https://supabase.com/docs/guides/auth/sessions (2026-11-08); GoTrue internal/conf/configuration.go (2026-11-08); supabase/config.toml · уверенность: high

### Free vs Pro — compute and connections
- Nano (Free): shared CPU, up to 0.5 GB RAM, recommended max DB 500 MB, 60 Postgres max connections, 200 pooler clients. Micro (default on paid): 2-core shared ARM, 1 GB RAM, ~$10/mo (covered by $10 compute credits on Pro), recommended ≤10 GB DB, 60 connections, 200 pooler clients. Small ~$15/mo, 2 GB, 90/400. Nano is not auto-upgraded when moving to Pro and is billed like Micro; compute change takes <2 min downtime. Pooler and connection limits are hard-coded per compute size.
- **Для нас:** The app talks to Postgres only via PostgREST/Auth/Storage (createClient / createAdminClient), never with direct pg connections, so the 60-connection cap is consumed by Supabase's own services and is not hit by 10 or 50 browsers. The real Free-plan risk is Nano's shared CPU/0.5 GB RAM under 50 concurrent users calling security-definer money functions + polling (lib/server/job-progress.ts) — undocumented, must be load-tested. Severity: medium on Free, low on Pro/Micro. Fix: run on Pro and after upgrading manually switch compute Nano→Micro in Settings > Compute and Disk (not automatic); keep polling intervals modest.
- Источник: https://supabase.com/docs/guides/platform/compute-and-disk (via docs MCP, 2026-11-08); https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits (2026-11-08) · уверенность: high

### Free vs Pro — database size, pausing, backups
- Free projects enter read-only mode when *database size* exceeds 500 MB (disk 1 GB); errors look like `cannot execute INSERT in a read-only transaction`. Pro: 8 GB disk included, auto-expands +50% at 90% (max 4 resizes per 24 h; at 95% with quota exhausted → read-only), $0.125/GB-month beyond 8 GB. Free projects 'that show low activity over a 7-day period' are paused (warning e-mail ~1 week before); restore via dashboard within 90 days (older doc copies say 1 year); paid projects are never paused. Free: database backups not downloadable; Pro: daily backups, PITR add-on. Fair Use on Free: notification, grace period, then restrictions (pausing, read-only, 402 on all API requests).
- **Для нас:** Workshops are weekly or less: on Free the project can be paused between sessions → Monday morning every login fails until the owner clicks 'Resume project' (several minutes). Severity: critical on Free (lesson breaks), none on Pro. Our tables (jobs, bot_messages, stars ledger) at 50 students grow slowly; 500 MB is months away, but a read-only flip would break every generation (insert into jobs/ledger) at once. Fix: Pro plan before the first paid workshop; if staying on Free for a test, open the dashboard or hit the API daily in the week before, and check DB size in Observability > Database.
- Источник: https://supabase.com/docs/guides/platform/database-size (2026-11-08); https://supabase.com/docs/guides/platform/free-project-pausing (2026-11-08); https://supabase.com/docs/guides/platform/billing-faq#fair-use-policy (2026-11-08); https://supabase.com/docs/guides/deployment/going-into-prod (2026-11-08) · уверенность: high

### Storage cost of 50 students × 50 MB montages per week
- Arithmetic from the official prices above: 50 × 50 MB = 2.5 GB uploaded per week (~10–11 GB/month). Uploads are free (ingress). ### Storage file size limits (global and bucket)
- Global file size limit: Free cannot exceed 50 MB; Pro/Team up to 500 GB (set in Storage Settings). Per-bucket `file_size_limit` cannot be higher than the global limit. Standard (single request) upload is recommended for files up to ~6 MB; resumable (TUS) uploads are recommended for files that may exceed 6 MB or on unstable networks, chunk size must be 6 MB, upload URL valid 24 h, and the direct storage host `https://<ref>.storage.supabase.co` should be used for large files. Signed upload URLs (`createSignedUploadUrl`) are valid for 2 hours; their token can also be passed as `x-signature` to the resumable endpoint.
- **Для нас:** supabase/migrations/20261101200000_init.sql:893-894 creates bucket `media` with 52428800 (50 MB) — the Free ceiling; after moving to Pro the *global* limit must also be ≥50 MB (it is by default on Free, verify after upgrade). Severity: medium at 50 (some students retry), low at 10. Fix: switch the browser upload to TUS (tus-js-client, `x-signature` = signed-upload token, 6 MB chunks, direct storage hostname) or at least add automatic retry with progress UI; keep bucket limit at 50 MB.

### Signed URL limits
- `createSignedUrl(s)` take `expiresIn` in seconds; no maximum expiry or per-call rate limit is documented. Signed URLs stay valid until expiry regardless of key changes; with Smart CDN (Pro) each unique `?token=` is a separate cache key, so a freshly signed URL is always a cache miss; cached copies can outlive token expiry until the cache TTL ends; deleting the object purges all cached entries within ~60 s.
- **Для нас:** lib/server/storage.ts:27-34 signs in chunks per request with TTL 1 h; gallery pages of 24 items (gallery.ts:25) re-sign on every render → every open of the gallery is a CDN miss and full uncached egress at 10 and 50 students. Severity: low (cost/perf only). Fix: cache signed URLs per (user, path) for ~50 min server-side or in the client, so repeated views reuse the same token; keep sensitive content behind short TTLs.
- Источник: https://supabase.com/docs/guides/storage/cdn/smart-cdn#signed-urls-and-cdn-caching (2026-11-08); https://supabase.com/docs/guides/storage/security/signing-keys (via WebSearch, 2026-11-08) · уверенность: medium

### PostgREST Max Rows (default 1000) and pagination
- Supabase projects return at most 1,000 rows per Data API request by default ('Max Rows' in Project Settings > Data API; PostgREST `db-max-rows`). A `.limit()` larger than Max Rows is silently capped; use `.range(from, to)` to page. Supabase recommends keeping the value low to bound payload size.
- **Для нас:** Already handled where it matters: lib/server/group-reports.ts:13-24 pages with PAGE=1000 and `range(from, from+PAGE-1)`; gallery uses 24-row pages (gallery.ts:25-39); lesson-progress limit 80. Two soft spots: (1) lib/server/bot/dal.ts:174 `.limit(1000)` on bot_leads — leads beyond 1000 are silently dropped from the teacher view (low, far future); (2) group-reports.ts:24 stops when `data.length < PAGE` — if an admin lowers Max Rows below 1000 in the dashboard, pagination ends after the first page and reports under-count (low). Fix: read PAGE from a single constant documented in setup.md as 'must equal Max Rows', or page until an empty result. At 10/50 students no table approaches 1000 rows per query. The owner's recollection of '10 000 rows' is wrong: it is 1,000.
- Источник: https://supabase.com/docs/reference/javascript/select (via WebSearch summary of official reference, 2026-11-08); https://docs.postgrest.org/en/stable/references/configuration.html#db-max-rows (2026-11-08) · уверенность: high

### Vercel egress IP and inbound client IP
- Vercel Functions send outbound requests from a dynamic range of addresses that can differ per invocation; Static IPs (fixed pair per region) are a Pro/Enterprise feature and do not cover Routing Middleware. Vercel sets `x-forwarded-for` on inbound requests to the real client IP (platform-controlled, spoofed values are overwritten).

### Server-side auth caching hazard
- Supabase warns that when a session is refreshed server-side the new tokens go out via Set-Cookie; if that response is cached by a CDN/ISR another user can receive someone else's session. `setAll` receives cache headers (Cache-Control/Expires/Pragma) that must be applied to the response in the proxy.
- **Для нас:** proxy.ts:51 already copies those headers onto the response, and lib/server/supabase/server.ts:23-31 wraps setAll in try/catch per the official pattern. Severity: none (verified correct). Keep this when refactoring; Next.js 16 cacheComponents must not cache any route that reads cookies().
- Источник: https://supabase.com/docs/guides/auth/server-side/creating-a-client#caching-considerations (2026-11-08) · уверенность: high

## Vercel, Next.js, kie, n8n

### Vercel Hobby — function max duration (Fluid compute)
- With Fluid compute (default for projects created after 2025-04-23), Hobby functions have a default AND maximum duration of 300 s; exceeding it returns 504 FUNCTION_INVOCATION_TIMEOUT. The 800 s / 1800 s extended maxima are Pro/Enterprise only. Legacy non-Fluid Hobby functions: default 10 s, max 60 s. Our routes export maxDuration = 60 (app/api/generate/route.ts:14, app/api/jobs/[id]/route.ts:14, app/api/b/[slug]/route.ts:23, app/api/b/[slug]/card/route.ts:18, app/api/tg/[botId]/route.ts:19), which is valid on both models.
- **Для нас:** Budget is adequate: text waits 50 s and createTask 45 s with retries (lib/server/gateway.ts TIMEOUT_MS / RETRY_BUDGET_MS) inside 60 s. If Fluid is ON (must be verified in Vercel project settings), maxDuration can be raised to up to 300 s for /api/jobs/[id] so the after() download of up to 100 MB (gateway.ts MAX_RESULT_BYTES) never gets cut; if the project is on legacy non-Fluid, 60 s is the hard ceiling and a slow 50–100 MB kie download would be killed, leaving the job in 'storing' until reclaimed 3 min later (job-rules.ts STORING_RECLAIM_AFTER_MS). Same at 10 and 50 users; severity medium.

### Vercel — function concurrency
- Functions auto-scale up to 30,000 concurrent executions on Hobby and Pro (100,000+ Enterprise). No separate lower per-project Hobby default was found in the docs.
